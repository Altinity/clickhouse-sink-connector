# Spec 01.08: Compressed Binary Log Transactions (`binlog_transaction_compression`, `Transaction_payload_event`)

## 1. Executive Summary & Purpose
Specifies how the lightweight connector replicates from a MySQL source whose binary log is written with `binlog_transaction_compression=ON` (MySQL 8.0.20+): the whole payload of a transaction arrives as ONE zstd-compressed `Transaction_payload_event`, the binlog client decodes it transparently, and Debezium dispatches the events it contains one by one. The connector needs no switch to consume it — detection is per event, by event type — but three things follow from the single outer event that the connector must get right and does not get for free: every row of every statement of the transaction carries the SAME binlog position (§3.2), a restart lands on the payload as a unit (§3.3), and the version sequence must therefore recognise "the rest of the same event" by position alone, never by row index (§3.5). This spec also declares the startup detection — the source's setting is read, the decoder is self-tested against a synthetic payload, the result is logged and exported as metrics, and `binlog.transaction.compression.check` lets an operator require compression (a WAN deployment that relies on it) or skip the probe (§3.4).

The motivation is bandwidth: on a wide-area link the binlog stream is the replication ceiling, and a row-based binlog compresses well — a 1.1 GB production binlog sample compressed 7.9x with zstd at level 3, the level `binlog_transaction_compression_level_zstd` defaults to. Payloads stay compressed on the wire (MySQL decompresses them only when an event has to be inspected), so enabling compression on the source shrinks what the connector pulls by that ratio with no connector-side setting.

## 3. Operational Specification

### 3.1 What the source writes
With `binlog_transaction_compression=ON` (a dynamic GLOBAL and SESSION variable, default OFF) MySQL compresses a transaction's payload with zstd at `binlog_transaction_compression_level_zstd` (1–22, default 3) just before commit and writes it as a single `Transaction_payload_event`. The MySQL reference manual (8.0 §7.4.4.5 "Binary Log Transaction Compression") fixes what is **never** compressed: events relating to the transaction's GTID (including anonymous GTID events); other control events such as view change and heartbeat events; incident events and the whole of any transaction containing them; non-transactional events and the whole of any transaction containing them (a transaction mixing transactional and non-transactional engines is written uncompressed); and events logged in statement-based format — compression applies to row-based logging only. Consequences the connector relies on:

1. A compressed transaction is delivered as `GTID_LOG_EVENT` (or `ANONYMOUS_GTID`), uncompressed, followed by ONE `TRANSACTION_PAYLOAD` event. The `BEGIN` query event, every `TABLE_MAP`, every rows event and the `XID` are INSIDE the payload.
2. Checksums: the source writes one checksum for the whole payload event and none for the events inside it.
3. The stream may be MIXED. Compression can be turned on or off at run time, per session as well as globally; a binlog can hold compressed and uncompressed transactions side by side, and a source that turned compression off still has compressed transactions in its older files. The connector therefore never keys any behaviour on the probed GLOBAL value (§3.4); it decodes each event by its type.
4. Size limits are measured on the compressed payload plus header against `max_allowed_packet` / `replica_max_allowed_packet`. The uncompressed size is a 32-bit quantity on the wire and the decoder allocates the whole uncompressed payload in memory (`ByteBuffer.allocate(uncompressedSize)`): a transaction whose uncompressed payload exceeds 2 GiB cannot be decoded (Debezium issue dbz#1503, fixed in 3.5); the connector's heap must hold the largest transaction's uncompressed payload in addition to Debezium's queue (spec 01.05 §3.4 item 8). Measured (§5, hard case H8): a 1.2M-row single-statement transaction (~150 MB uncompressed) is decoded and applied in 12–14 s with a 2 GiB heap and the connector's RSS at ~2.6 GB. Measured (H10): lowering the source's GLOBAL `max_allowed_packet` to 16 MiB did not stop a 24 MiB (incompressible) compressed payload from being streamed and applied — the dump connection is bounded by the replication packet limit, not by the sessions' `max_allowed_packet`; the connector does not have to be restarted for it.
5. MariaDB's `log_bin_compress` is a different on-disk format (compressed row events, not a payload event) and is out of scope; the preflight runs for MySQL only.

### 3.2 How it is decoded, and what that does to coordinates
The binlog client registers a deserializer for `TRANSACTION_PAYLOAD`. It reads the payload header as a sequence of type–length–value fields (1 = payload size, 2 = compression type, 3 = uncompressed size, 0 = end), reads the payload bytes, decompresses them with `Zstd.decompressByteArray` into a buffer of the declared uncompressed size, and deserializes binlog v4 events out of that buffer with a fresh `EventDeserializer` until it is exhausted — the result is an `ArrayList<Event>` of the transaction's inner events, carried by `TransactionPayloadEventData.getUncompressedEvents()`. Debezium's subclass additionally records every inner `TABLE_MAP` in its table-id map, so the row deserializers can resolve the rows events that follow inside the same payload.

Debezium then handles the outer event like any other in `handleEvent`: it stores the **outer** event's position (`setEventPosition(position, length)`), dispatches to `handleTransactionPayload`, and calls `completeEvent()` once. `handleTransactionPayload` loops over the inner events and calls the registered handler for each **directly** — the inner `BEGIN` starts the transaction (`handleTransactionBegin`), inner `TABLE_MAP`s update the schema map, inner rows events go through `handleChange` and emit change events, the inner `XID` commits. None of them passes through `handleEvent`, so:

1. **One position for the whole transaction.** `source.pos` of every row emitted from the payload is the payload event's position; `source.file` is the payload's file. Nothing in the change event says which inner event or which statement a row came from.
2. **The row index restarts at 0 in every inner rows event.** `handleChange` numbers rows within the event it is processing (`setRowNumber(rowIndex, numRows)`), and a multi-row statement larger than `binlog_row_event_max_size` is several rows events. So the sequence of `(file, pos, row)` the connector sees for one compressed transaction is `(F, P, 0..a), (F, P, 0..b), (F, P, 0..c), …` — non-monotonic in `row`, constant in `(F, P)`.
3. **The event counter does not advance inside the payload.** `completeEvent()` runs once, after the whole payload; the offset's `event` field stays at its pre-payload value for every row of the transaction.
4. **`ts_ms` is still per statement.** Each inner event keeps its own header timestamp; `source.ts_ms` behaves as in spec 01.04 (statement time, not commit time).

Without compression the same transaction is delivered as N distinct events at N distinct positions, each through `handleEvent`: the row index still restarts per event, but `pos` advances with it, so `(file, pos, row)` is monotonic within the transaction. Compression removes the `pos` advance and leaves only the restarting `row`. That is the one difference the connector has to absorb.

### 3.3 Restart inside a compressed transaction
Debezium's restart point for a transaction is the position of the event that opened it plus the number of events already completed and, for the event in progress, the number of rows already emitted (`eventsToSkipUponRestart`, `rowsToSkipUponRestart`). Under a payload the transaction opens on the inner `BEGIN`, whose position is the payload's; `completeEvent` never runs inside it; and `setRowNumber` counts rows of the inner event in progress. A durable offset taken while a payload is being applied is therefore `{file: F, pos: P, event: 0, row: k}` where `k` is the row index reached in the inner event that was being emitted, whichever inner event that was. On restart Debezium re-reads the payload from `P`, skips no events (`event = 0`), and skips `k` rows of the **first** rows event it meets (`startingRowNumber` applies once, then resets); every other row of the payload is delivered again.

That is at-least-once delivery, exactly as spec 02.04 §3.2 describes it, and it is safe for the same reason: the rows skipped had been written (the offset was committed only after the batch that contained them, spec 09.01), and the rows delivered again are versioned above everything the previous run wrote (the seeded floor, spec 02.02 §3.5), so `FINAL` resolves to the same row image. Nothing is skipped that was not written, because `k` never exceeds what was acknowledged and `startingRowNumber` skips rows of ONE event only. The cost is the redelivery of the rest of the payload — a whole transaction rather than the rest of one statement.

With GTID enabled the restart is positioned by the GTID set as before, and the same event/row skip applies within the resumed transaction. Observed (§5, hard case H9): after a kill -9 with ~150,000 of a 1.2M-row payload applied, the restart logged `Skip 0 events on streaming start` and `Skip 44 rows on streaming start` (GTID on; 22 rows GTID off) — the rows of the one inner event in progress — re-delivered the rest of the payload, and the replica converged to the source's 2,399,998 live rows with identical checksums.

### 3.4 Startup detection: the preflight, the flag, the metrics
`BinlogTransactionCompressionPreflight.check` runs once per engine start on a MySQL source (`connector.class` naming MySQL), after the row-image check and before the engine is built, in the mode `binlog.transaction.compression.check` selects:

| Mode | What runs | Source `ON` | Source `OFF` | Source unknown (older than 8.0.20, unreachable, not permitted) |
|---|---|---|---|---|
| `auto` (default) | decoder self-test, then the one `SELECT` | INFO: compression on, level, server version, decoder verified. **Refuses** if the self-test failed — the source will send payloads this build cannot decode, and the failure would otherwise surface as a deserialization error mid-stream | INFO: decoder ready should the source enable it (it is dynamic; a session-level `ON` also produces payloads). WARN banner if the self-test failed | WARN and continue; refuses only if the self-test also failed |
| `require` | same | as `auto` | **Refuses**: the deployment relies on compression (a WAN link); message quotes `SET PERSIST binlog_transaction_compression = ON` and the `my.cnf` key | **Refuses** |
| `skip` | nothing | — | — | — |

An unrecognised mode refuses startup naming the three values. The probe is read-only and issues exactly one statement (through `KeylessTablePreflight.assertReadOnlySql`), never a `SET`: the connector cannot and does not turn compression on — that is the source operator's change — it reports whether the source has it and proves it can consume it. The self-test proves the whole chain a compressed transaction needs: the zstd-jni classes, a loadable native library for this platform, and the binlog client's decoder, by decoding a synthetic payload (one XID event inside a zstd frame) through the real `TransactionPayloadEventDataDeserializer`.

Three gauges are set after the probe (never in `skip`): `clickhouse_sink_source_binlog_transaction_compression` (1 ON, 0 OFF, -1 unknown), `clickhouse_sink_source_binlog_transaction_compression_level_zstd` (-1 unknown), `clickhouse_sink_binlog_payload_decoder_ok` (1 passed, 0 failed). They are set on every engine start, so a source change picked up at the next restart is visible; between restarts the value is what the source reported when this engine started.

Per-event observability (how many payloads were decoded, compressed vs uncompressed bytes) is not available to the connector: the change event does not say whether its row came from a payload, and the embedded engine exposes no hook on the binlog client. The source side has it (`Transaction_payload_event` rows in `SHOW BINLOG EVENTS`, the compressed/uncompressed sizes in `mysqlbinlog --verbose`); the end-to-end harness (§5) uses the former as its proof that compression was exercised.

### 3.5 Versioning: the rest of the same event is not a redelivery
The version sequence (spec 02.02 §3.1) classifies a positioned record against the run's high-water mark: above it — first delivery, floored; the same event — the rest of that event, floored at what its first row received (§3.1.2); below it — redelivery, not floored. "The same event" is decided by `SourcePosition.sameLogPosition` — same log, same file, same byte position, **any row index** (spec 01.02 §3.3) — and that test is made BEFORE the above/below comparison.

The row index cannot take part in that decision. Under a payload the second statement's rows arrive at `(F, P, 0)` when the mark is `(F, P, a)` from the first statement's last row; by `compareTo` they rank below the mark. If they were treated as redeliveries they would keep their raw statement time while the first statement's rows had been floored, and a transaction that inserted, updated and deleted one key would version its INSERT above its own UPDATE and DELETE: the update lost, the deleted row live, row counts intact. Two things make that concrete rather than theoretical: the floor is above the raw statement time exactly when it matters — after every restart, when it is seeded from the durable mark (about one to six source seconds above the last version) or from the connector clock plus five seconds on the first start after an upgrade (spec 02.02 §3.5) — and one large multi-row statement is by itself several rows events with restarting row indexes, so a plain bulk `INSERT … VALUES` followed by an `UPDATE` in the same transaction is enough. Both paths are affected, because the GTID path versions with the same clamped timestamp (spec 02.01 §3.1).

With the same-event rule every row of a compressed transaction is floored at what its first row received and versioned by the strictly increasing counter, in delivery order — which is binlog order, which is commit order. The mark is left at the first row that set it; a redelivery of the whole transaction (engine retry without a restart) meets the same mark and takes the same clamp, so the assignment stays redelivery-stable (spec 02.04 §3.3). A redelivery from an EARLIER event keeps the un-floored, source-timestamp anchored assignment, whatever its row index. Uncompressed multi-row events, which always had rows above the mark at the same position, receive exactly the versions they received before (the first-delivery clamp to `sequenceMaxSourceTs` and the same-event clamp to `sequenceHighWaterEffectiveTs` coincide within one transaction, because no other record is versioned between two rows of one transaction).

### 3.6 What does not change
Schema evolution, DDL handling, the DDL barrier, TRUNCATE, keyless tables, offsets and the durable version mark are untouched: a DDL is its own (uncompressed, statement-format) transaction and reaches the dispatch loop as before; inner rows events are dispatched to the same handlers as uncompressed ones. The connector's own writes to ClickHouse are identical in shape and content for a compressed and an uncompressed delivery of the same transaction — compression is a property of the transport from the source, invisible in the replica.

## 4. Invariants Preserved
- **Invariant I1 (Log Sequence Monotonicity)** and **I2 (Deterministic Version Monotonicity)**: within a compressed transaction delivery order is binlog order, and the same-event rule keeps the versions of its rows strictly increasing above the floor; across transactions the first row of the next payload is a first delivery above the mark.
- **Invariant I8 (Durable Offset Quiescence)**: an offset inside a payload never advances past an unwritten row (§3.3); a restart re-delivers, never skips.
- **Invariant I9 (Loud Failure)**: a source that compresses while the decoder is unavailable refuses at start, with the fix in the message, instead of failing on the first payload with a deserialization error; `require` refuses a source that does not compress.
- **Invariant I11 (Drop-in Upgrade Safety)**: the version formula, seeds and domain are unchanged (spec 02.01 §4); only the classification of same-event rows changed, and only for rows that were mis-classified.
- **Read-only against the source**: the preflight issues one `SELECT` and never a `SET`; compression is enabled by the source operator, never by the connector.

- `BinlogTransactionCompressionPreflightTest.sourceOnIsReportedAndDecoderVerified()`, `BinlogTransactionCompressionPreflightTest.sourceOffAutoIsQuiet()`, `BinlogTransactionCompressionPreflightTest.sourceOffRequireRefuses()`, `BinlogTransactionCompressionPreflightTest.sourceUnknownAutoWarnsAndContinues()`, `BinlogTransactionCompressionPreflightTest.sourceUnknownRequireRefuses()`, `BinlogTransactionCompressionPreflightTest.skipIssuesNoQueryAndNoSelfTest()`, `BinlogTransactionCompressionPreflightTest.unknownModeRefuses()`, `BinlogTransactionCompressionPreflightTest.nonMySqlConnectorIsUntouched()` — the decision table of §3.4, row by row, against a stubbed source that answers the one permitted query or fails it.
- `BinlogTransactionCompressionPreflightTest.metricsUpdateIsANoOpWhenMetricsAreOff()` — the gauges are optional instrumentation, never a startup dependency.
- `SourcePositionTest.sameLogPositionIgnoresTheRowIndex()` — spec 01.02 §3.3: same file and position with a higher or a restarted row index is the same event; another position, file or log is not; LSNs compare on the LSN.
- `CommitOrderVersionClampTest.laterStatementsOfACompressedTransactionShareTheFirstStatementsFloor()` — §3.5: a 3-row INSERT then an UPDATE and a DELETE at one position, delivered after a newer commit raised the floor: the UPDATE and DELETE are floored like the INSERT and out-rank it (pre-fix: they kept their raw second and lost).
- `CommitOrderVersionClampTest.chunksOfOneLargeStatementShareTheFloor()` — §3.2 item 2 / §3.5: three rows-event chunks of one statement at one position, each restarting at row 0, all floored and strictly increasing; the next transaction is a first delivery above them.
- `CommitOrderVersionClampTest.redeliveryFromAnEarlierPositionIsStillNotClamped()` — the redelivery branch is intact: an earlier event redelivered with any row index keeps the source-timestamp anchored assignment (spec 02.04 §3.3).
- `CommitOrderVersionClampTest.rowsOfOneTransactionShareTheFirstRowsFloor()`, `CommitOrderVersionClampTest.rowsWithinOneEventAreFirstDeliveries()` — the pre-existing same-position and multi-row-event pins receive the same versions as before (§3.5, last paragraph).
- Lean: `Replication.VersionFloor.same_event_rows_share_floor` — a record at the mark's position is versioned at least at the floor the mark's first row received; `Replication.VersionFloor.compressed_transaction_example` — the executed scenario of §3.5 (INSERT rows, UPDATE, DELETE at one position after a newer commit): strictly increasing versions; `Replication.VersionFloor.compressed_transaction_inverts_without_same_event_rule` — the pre-fix classification on the same scenario versions the UPDATE below the INSERT.
- End-to-end (`sink-connector-lightweight/tests/e2e/binlog_transaction_compression.sh`, MySQL 8.0 with `binlog_transaction_compression=ON`, GTID on and off, ClickHouse 24.8, value-level comparison of every table): steady-state compressed transactions including a 300,000-row single-statement transaction, a session-level compression toggle, DDL followed by DML, keyless tables; a kill -9 followed by a compressed multi-statement transaction written before the restart under a mark-seeded and under a clock-seeded floor (§3.5); a kill -9 while a 400,000-row compressed transaction is being applied (§3.3); and the source-side proof that `Transaction_payload` events were present. The pre-fix build fails the §3.5 restart cases (the UPDATE after a multi-row INSERT is lost and the DELETE's row stays live); the fixed build passes every case with identical row counts and checksums.
- Hard and edge cases (`sink-connector-lightweight/tests/e2e/binlog_transaction_compression_hard.sh`, same stack, GTID on and off, `binlog.transaction.compression.check=require`, 49 checks each, all passing on the fixed build): H1 multi-table transaction with `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` (rolled-back rows never reach the replica); H2 a long transaction that commits after short ones executed later (the late payload's tail UPDATE/DELETE win); H3 forty 1 MiB rows in one payload at session zstd level 22 with an UPDATE and a DELETE at the tail; H4 an InnoDB + MyISAM transaction (written uncompressed by MySQL, §3.1) followed by a compressed one on the same keys; H5 `binlog_rows_query_log_events=ON` (`Rows_query` events inside the payload); H6 `SET GLOBAL binlog_transaction_compression` turned OFF and back ON at run time with transactions on both sides of each switch; H7 a keyless table with duplicate rows and a `LIMIT 1` delete inside one payload; H8 a 1.2M-row single-statement transaction (§3.1 item 4); H9 kill -9 while a second 1.2M-row payload is being applied (§3.3); H10 source `max_allowed_packet` lowered to 16 MiB under a 24 MiB incompressible payload (§3.1 item 4); H11 `ADD COLUMN`, `MODIFY COLUMN`, `DROP COLUMN`, each followed by a compressed multi-statement transaction on the changed table; H12 kill -9 right after a compressed transaction (offset at its payload), then `TRUNCATE` and `DROP TABLE` while down.
