# Spec 01.08: Compressed Binary Log Transactions (`binlog_transaction_compression`, `Transaction_payload_event`)

## 1. Executive Summary & Purpose
Specifies how the lightweight connector replicates from a MySQL source whose binary log is written with `binlog_transaction_compression=ON` (MySQL 8.0.20+): the whole payload of a transaction arrives as ONE zstd-compressed `Transaction_payload_event`, the binlog client decodes it transparently, and Debezium dispatches the events it contains one by one. The connector needs no switch to consume it — detection is per event, by event type — but four things follow from the single outer event that the connector must get right and does not get for free: the payload must be decoded as a STREAM, one inner event at a time, so a transaction of any uncompressed size is replicated with constant memory (§3.2.1); every row of every statement of the transaction carries the SAME binlog position (§3.2), a restart lands on the payload as a unit (§3.3), and the version sequence must therefore recognise "the rest of the same event" by position alone, never by row index (§3.5). This spec also declares the startup detection — the source's setting is read, the decoder is self-tested against a synthetic payload, the result is logged and exported as metrics, and `binlog.transaction.compression.check` lets an operator require compression (a WAN deployment that relies on it) or skip the probe (§3.4).

The motivation is bandwidth: on a wide-area link the binlog stream is the replication ceiling, and a row-based binlog compresses well — a 1.1 GB production binlog sample compressed 7.9x with zstd at level 3, the level `binlog_transaction_compression_level_zstd` defaults to. Payloads stay compressed on the wire (MySQL decompresses them only when an event has to be inspected), so enabling compression on the source shrinks what the connector pulls by that ratio with no connector-side setting.

**Verification note (Debezium 3.1.3.Final → 3.7.0.Final upgrade, PR #1558).** This spec was written against embedded Debezium 3.1.3.Final, where `handleTransactionPayload` dispatches every inner event of a `TRANSACTION_PAYLOAD` directly to its handler, bypassing `handleEvent`/`completeEvent` entirely (§3.2's "calls the registered handler for each directly" paragraph, confirmed in Debezium 3.1.3 source). **That changed in Debezium 3.3.2.Final and is unchanged in 3.7.0.Final** (confirmed by direct diff of `BinlogStreamingChangeEventSource.handleTransactionPayload` across 3.1.3/3.3.2/3.7.0 sources): inner events are now routed through `handleEvent(partition, offsetContext, context, event)` like top-level events, so `completeEvent()` runs once per inner event, not once per payload, and `handleEvent`'s `setEventPosition` call is now guarded (`if (trackableEventHeader.getPosition() > 0)`) so an inner event's `position=0` no longer overwrites the tracked binlog position. §3.2 item 3 and the restart narrative of §3.3 below are corrected for 3.7 behavior; the exact restart log text and RTO numbers of §5/§6 were measured on the 3.1.3 build and have **not** been re-measured against 3.7.0.Final in this exercise — re-running the hard/large/chaos harnesses (H9, F1, F9, L3) against the 3.7 jar is an open follow-up (§6, FM-01.08-8 lists the one new hazard found by source analysis: a connector built on Debezium ≥3.3 that crashes mid-payload and is then resumed by a connector built on Debezium <3.3, as would happen during a manual rollback of this upgrade, can silently drop the rest of an in-flight compressed transaction).

## 3. Operational Specification

### 3.1 What the source writes
With `binlog_transaction_compression=ON` (a dynamic GLOBAL and SESSION variable, default OFF) MySQL compresses a transaction's payload with zstd at `binlog_transaction_compression_level_zstd` (1–22, default 3) just before commit and writes it as a single `Transaction_payload_event`. The MySQL reference manual (8.0 §7.4.4.5 "Binary Log Transaction Compression") fixes what is **never** compressed: events relating to the transaction's GTID (including anonymous GTID events); other control events such as view change and heartbeat events; incident events and the whole of any transaction containing them; non-transactional events and the whole of any transaction containing them (a transaction mixing transactional and non-transactional engines is written uncompressed); and events logged in statement-based format — compression applies to row-based logging only. Consequences the connector relies on:

1. A compressed transaction is delivered as `GTID_LOG_EVENT` (or `ANONYMOUS_GTID`), uncompressed, followed by ONE `TRANSACTION_PAYLOAD` event. The `BEGIN` query event, every `TABLE_MAP`, every rows event and the `XID` are INSIDE the payload.
2. Checksums: the source writes one checksum for the whole payload event and none for the events inside it.
3. The stream may be MIXED. Compression can be turned on or off at run time, per session as well as globally; a binlog can hold compressed and uncompressed transactions side by side, and a source that turned compression off still has compressed transactions in its older files. The connector therefore never keys any behaviour on the probed GLOBAL value (§3.4); it decodes each event by its type.
4. Size limits. MySQL measures its packet limits on the COMPRESSED payload plus header (the manual: "`max_allowed_packet` and `replica_max_allowed_packet` … are measured on the compressed size of the `Transaction_payload_event`, plus the bytes used for the event header"; both are capped at 1 GiB; measured H10: lowering the source's GLOBAL `max_allowed_packet` to 16 MiB did not stop a 24 MiB compressed payload, so the sessions' value is not what bounds the dump connection). That compressed-size ceiling is the source's own and applies identically to a MySQL replica ("a large transaction which can be replicated successfully when binary log transaction compression is not in use, might stop replication due to its size when binary log transaction compression is in use"); on a source older than 8.0.34 it is the only size limit a compressed transaction has on this path. **From MySQL 8.0.34 (and 8.1.0) the server removes that ceiling itself**: the release note of Bug #33588473 reads "Now, when the compressed data grows larger than 1 GiB, we fall back to processing the transaction without any compression", i.e. such a transaction is written as ordinary, individually packetized events. Measured (§5, large case L5, 1,316,800,147 bytes of incompressible data in one transaction): MySQL 8.0.46 and Percona Server 8.0.35 write it uncompressed (`performance_schema.binary_log_transaction_compression_stats` counts it under `COMPRESSION_TYPE=NONE`; `SHOW BINLOG EVENTS` shows `Write_rows` events, no `Transaction_payload`) and the connector replicates it value-exact; Percona Server 8.0.32 writes the same transaction as ONE 1,316,830,342-byte ZSTD `Transaction_payload`, on which `SHOW BINLOG EVENTS` fails with `ERROR 1220 ... Event too big` -- no reader can receive it. So on 8.0.34+ a transaction of any size replicates: a compressed payload is at most 1 GiB and is streamed (§3.2.1), anything larger arrives uncompressed; on 8.0.20-8.0.33 the preflight warns (`auto`) or refuses (`require`, §3.4). The UNCOMPRESSED size is unbounded for the connector: the payload header's uncompressed-size field is a length-encoded integer of up to 8 bytes, read as 64 bits, and the payload is decoded as a stream (§3.2.1), so the connector's heap holds the compressed payload (≤ 1 GiB) plus the decompressor's window plus ONE inner event, whatever the transaction's uncompressed size. (Historical: the stock decoder — Debezium 3.1.3 `TransactionPayloadDeserializer`, binlog client 0.40.2 — read that field with `readPackedInteger` and threw `IOException: Stumbled upon long even though int expected` above 2,147,483,647 bytes, then decompressed the whole payload into one array (`ByteBuffer.allocate(uncompressedSize)`) and materialized every inner event; a transaction above 2 GiB uncompressed stopped the connector permanently at that position, and one below it cost its whole uncompressed size in heap. Debezium's own later change, dbz#1503 in 3.5, reads the field as a long but still refuses above `Integer.MAX_VALUE` with "Cannot process event … larger than max array size".) Measured (§5, hard case H8): a 1.2M-row single-statement transaction (~150 MB uncompressed) is decoded and applied in 12–14 s with a 2 GiB heap. Measured (large cases, §5): single transactions of 2,395,580,867 and 4,606,880,870 bytes uncompressed (past `Integer.MAX_VALUE` and past 2^32; 38 MB and 73 MB compressed) replicate value-exact with a 2 GiB connector heap in 37 s and 54 s, the connector container at 2.3–2.6 GB for both sizes, including a kill -9 in the middle of one.
5. MariaDB's `log_bin_compress` is a different on-disk format (compressed row events, not a payload event) and is out of scope; the preflight runs for MySQL only.

### 3.2 How it is decoded, and what that does to coordinates
Debezium registers a deserializer for `TRANSACTION_PAYLOAD` by class name, and in this connector that class is the connector's own streaming decoder (§3.2.1). It reads the payload header as a sequence of type–length–value fields (1 = payload size, 2 = compression type, 3 = uncompressed size, 0 = end; MySQL writes 2, 3, 1) and keeps the payload bytes; the transaction's inner events are handed out by `TransactionPayloadEventData.getUncompressedEvents()`, and every inner `TABLE_MAP` is recorded in Debezium's table-id map before the rows events after it are parsed, so the row deserializers resolve the rows events that follow inside the same payload.

#### 3.2.1 Streaming: any uncompressed size, constant memory
The decoder never holds a transaction uncompressed. Its contract:

1. **Header.** Sizes are read as 64-bit length-encoded integers (`TransactionPayloadDeserializer.deserialize(ByteArrayInputStream)`). The uncompressed-size field may be absent only for compression type NONE, where it defaults to the payload size (MySQL's encoder omits it exactly there: `libbinlogevents/src/codecs/binary.cpp`, `Transaction_payload::encode`, 8.0.41 -- `if (ev.get_compression_type() != transaction::compression::type::NONE)`); a ZSTD payload without it is refused with `PayloadEventDecodingException`, because the end-of-pass size check (item 5) is what makes a stream cut at a zstd frame boundary fail instead of decoding to a shorter transaction. Compression type `0` (ZSTD) and `255` (NONE, raw bytes) are accepted; any other type, a missing payload-size field, a payload size larger than the event carries, or a size field above 2^63 is refused with `PayloadEventDecodingException`.
2. **What is retained.** The compressed payload bytes (bounded by the source's packet limits, at most 1 GiB, §3.1 item 4) and nothing else. `getUncompressedEvents()` returns a `StreamedPayloadEvents`: an iteration-only list.
3. **A pass.** Each `StreamedPayloadEvents.iterator()` opens a fresh zstd stream over the retained bytes (window up to 2^31, so every level 1–22 MySQL can write; concatenated frames are one stream) behind a 64 KiB buffer, and each `next()` reads ONE binlog v4 event: its header, then its body. Nothing of an earlier event is kept by the list. A pass therefore holds the compressed payload, the decompressor's window (≤ 128 MiB at level 22, 2 MiB at the default level 3) and one event.
4. **TABLE_MAP eager, everything else lazy.** A `TABLE_MAP` is parsed as it is read and recorded in the shared table-id map before it is returned. Every other inner event is a `LazyPayloadEvent`: its body is parsed on the first `LazyPayloadEvent.getData()`, with the inner-event deserializer Debezium's class used (Debezium's `RowDeserializers` for the six rows types over the shared map, the binlog client's defaults for the rest). Why: the inner events are iterated THREE times per payload — the binlog client's `EventDeserializer.deserializeTransactionPayloadEventData` and Debezium's `createEventDeserializer` subclass each walk them to register TABLE_MAPs, then `handleTransactionPayload` walks them to dispatch. The two registration passes call `getData()` only on TABLE_MAPs, so they cost a decompression and a header read per event, never a row parse; the dispatch pass parses each body exactly once. The events dispatched are, field for field, the events the stock decoder produced (same headers, same deserializers, same order).
5. **Integrity, loudly.** At the end of every pass the number of bytes decompressed is compared with the header's uncompressed size (or the payload size for NONE); a mismatch, a truncated or corrupt frame, an inner event cut short, an inner event declaring an impossible length, or a `TRANSACTION_PAYLOAD` nested inside a payload throws `PayloadEventDecodingException` from `next()`; a body that does not parse throws it from `getData()`. Debezium treats either as an error processing the payload event and stops the engine; the offset has not advanced past the payload's last acknowledged row (§3.3), so a restart re-reads the payload and fails the same way until the cause is fixed — a compressed transaction is never partially skipped. (The stock decoder's behaviour on a body that does not parse was different: the failure surfaced inside `nextEvent`, where Debezium converts a non-I/O deserialization failure into an `INCIDENT` pseudo-event handled per `event.deserialization.failure.handling.mode` — under `warn`/`skip` the WHOLE transaction was dropped. The streaming decoder stops in every mode; with the default `fail` the outcome is the same, a stop.) The native decompressor is closed at the end of each pass and, for a pass abandoned by an exception, by a `java.lang.ref.Cleaner`.
6. **Iteration only.** `StreamedPayloadEvents` extends `ArrayList` only because the binlog client's type says so. For-each, `forEach` and `stream()` iterate; `size()`, `get()`, `isEmpty()`, `toArray()`, copying, `listIterator()` and every mutator throw `UnsupportedOperationException` — the inherited implementations would silently answer from an empty backing array. Neither the list's nor the event data's `toString()` iterates.
7. **Cost.** Two extra decompression passes (the registration passes) per payload; zstd decompresses at over 1 GB/s per core, and the passes read no row data. Measured: a 2,458,500,143-byte transaction (1.2M rows, 31 MB compressed) is decoded — both passes and the dispatch pass — in 2.8 s with a 512 MiB heap, peak heap use 284 MiB.
8. **Not serializable.** `StreamedPayloadEvents`, `LazyPayloadEvent` and `StreamingTransactionPayloadEventData` inherit `Serializable` from the binlog client's types but keep their decoding state `transient` (the retained bytes, the deserializers, the shared table-id map). Each declares `writeObject`/`readObject`/`readObjectNoData` that throw (`NotSerializableException` on write), so a future serializer fails at write time with the reason instead of producing a copy that NPEs when iterated. Nothing in Debezium or the binlog client serializes these objects today.

The decoder is not thread-safe; like the one it replaces it runs on the binlog reader thread.

Debezium handles the **outer** `TRANSACTION_PAYLOAD` event in `handleEvent` like any other: it stores the outer event's position (`setEventPosition(position, length)`), dispatches to `handleTransactionPayload`, and calls `completeEvent()` for it. As of Debezium 3.3.2.Final (unchanged in 3.7.0.Final; this repository upgraded from 3.1.3.Final to 3.7.0.Final in PR #1558), `handleTransactionPayload` no longer calls the registered handlers directly — it calls `handleEvent(partition, effectiveOffsetContext, context, uncompressedEvent)` for **every inner event**, the same entry point top-level events use: the inner `BEGIN` starts the transaction (`handleTransactionBegin`), inner `TABLE_MAP`s update the schema map, inner rows events go through `handleChange` and emit change events, the inner `XID` commits — and each of these now runs inside its own `handleEvent` call, including its own `completeEvent()`. Debezium's own `handleEvent` guards the position write for this reason: `setEventPosition` only takes effect `if (trackableEventHeader.getPosition() > 0)`, since every inner event's header carries `position = 0`. (On 3.1.3.Final, which this spec was first written against, `handleTransactionPayload` dispatched directly to the handlers, bypassing `handleEvent`/`completeEvent` for every inner event; see the verification note above.) Net effect, verified against 3.7.0.Final source (`BinlogStreamingChangeEventSource`, `BinlogOffsetContext`, both unchanged in field semantics from 3.1.3 — only the call pattern around them changed):

1. **One position for the whole transaction, still.** The position guard means an inner event's `position = 0` never overwrites the tracked position, so `source.pos`/`source.file` of every row emitted from the payload is still the outer payload event's position. Nothing in the change event says which inner event or which statement a row came from.
2. **The row index restarts at 0 in every inner rows event, still.** `handleChange` numbers rows within the event it is processing (`setRowNumber(rowIndex, numRows)`), and a multi-row statement larger than `binlog_row_event_max_size` is several rows events. So the sequence of `(file, pos, row)` the connector sees for one compressed transaction is `(F, P, 0..a), (F, P, 0..b), (F, P, 0..c), …` — non-monotonic in `row`, constant in `(F, P)`, exactly as before.
3. **The event counter DOES advance inside the payload (changed from 3.1.3; corrected 2026-10, PR #1558 regression sweep).** `completeEvent()` now runs once per inner event — BEGIN, each TABLE_MAP, each rows event, XID — not once for the whole payload. The offset's `event` field (`restartEventsToSkip`) therefore counts inner events completed since the payload started, not "0" for the payload's whole duration. This does not change `(file, pos, row)` (item 1-2 are unaffected: `completeEvent()` does not touch position), and on a Debezium ≥3.3 connector restarting its own crash it makes the restart MORE precise, not less (§3.3): the connector now skips exactly the inner events already completed (`initialEventsToSkip`/`skipEvent`, consulted by `handleChange`'s own `if (skipEvent) { return; }` guard) instead of redelivering every rows event up to and including the one in progress. The one place this is NOT safe is a cross-version restart where the offset was written by a ≥3.3 engine (non-zero `event`) and is then read by a <3.3 engine (3.1.3 or earlier, whose `handleTransactionPayload` does not call `handleEvent` for inner events and therefore never decrements `initialEventsToSkip` or clears `skipEvent` inside a payload) — see FM-01.08-8.
4. **`ts_ms` is still per statement.** Each inner event keeps its own header timestamp; `source.ts_ms` behaves as in spec 01.04 (statement time, not commit time).

Without compression the same transaction is delivered as N distinct events at N distinct positions, each through `handleEvent`: the row index still restarts per event, but `pos` advances with it, so `(file, pos, row)` is monotonic within the transaction. Compression removes the `pos` advance and leaves only the restarting `row`. That is the one difference the connector has to absorb.

### 3.3 Restart inside a compressed transaction

**On Debezium 3.3.2.Final and 3.7.0.Final (this repository as of PR #1558).** Debezium's restart point for a transaction is the position of the event that opened it, the number of inner events already completed (`eventsToSkipUponRestart`), and, for the event in progress, the number of rows already emitted (`rowsToSkipUponRestart`). Because inner events now run through `handleEvent`/`completeEvent` (§3.2 item 3), a durable offset taken while a payload is being applied is `{file: F, pos: P, event: n, row: k}` where `n` is the count of inner events (BEGIN, TABLE_MAPs, completed rows events, …) already completed inside this payload and `k` is the row index reached in the inner event in progress. On restart of a same-or-newer (≥3.3) connector, Debezium re-reads the payload from `P`, sets `initialEventsToSkip = n` and `skipEvent = true` (via `handleTransactionBegin`'s `if (initialEventsToSkip != 0)`), and for each inner event: if `skipEvent` is still true it decrements `initialEventsToSkip` and, for a rows event, returns from `handleChange` without touching a row (`if (skipEvent) { return; }`); once `initialEventsToSkip` reaches 0, `skipEvent` clears and the next rows event resumes at `startingRowNumber = k`. This skips **exactly** the `n` inner events already completed and resumes the in-progress one at row `k` — strictly more precise than a payload with multiple rows events under the historical (3.1.3) behavior described below, which could not distinguish which rows event was in progress and so replayed every rows event up to and including it.

(Historical, Debezium 3.1.3.Final, this spec's original basis: `completeEvent` never ran inside a payload, so a durable offset read `{file: F, pos: P, event: 0, row: k}` regardless of which inner event was in progress. On restart Debezium skipped no events (`event = 0`) and skipped `k` rows of the **first** rows event it met (`startingRowNumber` applies once, then resets); every other rows event of the payload — including ones already fully applied before the crash — was delivered again in full.)

Either way this is at-least-once delivery, exactly as spec 02.04 §3.2 describes it, and it is safe for the same reason: the rows skipped had been written (the offset was committed only after the batch that contained them, spec 09.01), and the rows delivered again are versioned above everything the previous run wrote (the seeded floor, spec 02.02 §3.5), so `FINAL` resolves to the same row image. Nothing is skipped that was not written: on 3.1.3, `k` never exceeded what was acknowledged and `startingRowNumber` skipped rows of ONE event only; on ≥3.3, `n` and `k` together describe exactly the prefix of the payload already completed. The remaining cost on ≥3.3 is redelivery of the ONE in-progress rows event's un-acknowledged tail, where 3.1.3 cost redelivery of the whole payload from its first rows event.

**Cross-version restart hazard (new in this upgrade, not previously documented — see FM-01.08-8; corrected 2026-10, PR #1558 regression sweep — the first pass of this paragraph understated the blast radius, see below).** The precise ≥3.3 skip above depends on the SAME dispatch path writing `n` and later reading it: `handleTransactionBegin`'s `initialEventsToSkip != 0` check only engages `skipEvent`, and only a `handleEvent`-routed inner dispatch ever clears it again. A <3.3 connector (3.1.3.Final, as shipped before PR #1558, or any earlier Debezium) reading an offset with `event = n > 0` — written by a ≥3.3 connector that crashed mid-payload — sets `skipEvent = true` at the inner `BEGIN` (dispatched directly, not through `handleEvent`) and then **never clears it inside that payload via a decrement**, because none of 3.1.3's direct inner dispatches run the `handleEvent` decrement logic. Every rows event of the WHOLE payload is therefore skipped outright (`handleChange`'s `if (skipEvent) { return; }`), including the in-progress one and anything after it. Critically, `initialEventsToSkip` is **not decremented at all** for this payload, not even by 1: `handleTransactionCompletion` (run for the inner `XID`, same as for a normal top-level commit) unconditionally sets `skipEvent = false` as part of finishing the transaction, and this happens *inside* the direct-dispatch loop, i.e. *before* the OUTER `handleEvent` call (the one processing the `TRANSACTION_PAYLOAD` event itself) reaches its own post-dispatch `if (skipEvent) { --initialEventsToSkip; ... }` check. That check therefore always finds `skipEvent` already `false` and decrements nothing. The full budget `n` survives completely intact into the NEXT top-level binlog event. If that next event is itself another compressed `TRANSACTION_PAYLOAD`, the identical sequence repeats in full: the new payload's inner `BEGIN` re-arms `skipEvent` (since `initialEventsToSkip` is still `n != 0`), every one of ITS rows events is skipped too, its inner `XID` resets `skipEvent = false` again, and the outer event's post-check again decrements nothing — `n` survives unchanged. **This repeats for every subsequent fully-compressed transaction, indefinitely, with zero data from any of them ever applied**, until a top-level (uncompressed) transaction's own events are processed under the armed flag: an uncompressed transaction's `BEGIN` and each of its rows events ARE routed through `handleEvent` individually (they are top-level binlog events, not direct-dispatched inner ones), so each one that runs while `skipEvent` is true DOES decrement `initialEventsToSkip` by 1 — but a transaction's own `XID`/commit also resets `skipEvent = false` early if it fires before the budget reaches 0, so if `n` is larger than one uncompressed transaction's own event count, the NEXT uncompressed transaction's `BEGIN` has to re-arm `skipEvent` before its events can keep consuming the remaining budget. The `n`-sized budget can therefore end up spent against events spread across several subsequent uncompressed transactions, not a fixed `n - 1` against whatever immediately follows. This is a genuine data-loss path, triggered only by downgrading from a Debezium ≥3.3 build (this branch, post-upgrade) to a <3.3 build (2.11.0 and earlier) while resuming an offset written mid-compressed-payload. Not applicable in the other direction (§3.2 item 3's note): a <3.3-written offset always has `event = 0`, so a ≥3.3 connector reading it takes the `initialEventsToSkip == 0` branch, never sets `skipEvent`, and degrades to the historical whole-payload-redelivery behavior above — safe, just imprecise.

With GTID enabled the restart is positioned by the GTID set as before, and the same event/row skip applies within the resumed transaction. Historically observed on the pre-upgrade (3.1.3) build (§5, hard case H9): after a kill -9 with ~150,000 of a 1.2M-row payload applied, the restart logged `Skip 0 events on streaming start` and `Skip 44 rows on streaming start` (GTID on; 22 rows GTID off) — the rows of the one inner event in progress — re-delivered the rest of the payload, and the replica converged to the source's 2,399,998 live rows with identical checksums. **This has not been re-run against the 3.7.0.Final build in this exercise**; on 3.7 the same scenario is expected to log `Skip <n> events on streaming start` with `n > 0` (the inner events of the payload completed before the kill), per the corrected mechanism above — stated as an expectation from source analysis, not an observed result.

### 3.4 Startup detection: the preflight, the flag, the metrics
`BinlogTransactionCompressionPreflight.check` runs once per engine start on a MySQL source (`connector.class` naming MySQL), after the row-image check and before the engine is built, in the mode `binlog.transaction.compression.check` selects:

| Mode | What runs | Source `ON` | Source `OFF` | Source unknown (older than 8.0.20, unreachable, not permitted) |
|---|---|---|---|---|
| `auto` (default) | decoder self-test, then the one `SELECT` | INFO: compression on, level, server version, decoder verified. **Refuses** if the self-test failed — the source will send payloads this build cannot decode, and the failure would otherwise surface as a deserialization error mid-stream | INFO: decoder ready should the source enable it (it is dynamic; a session-level `ON` also produces payloads). WARN banner if the self-test failed | WARN and continue; refuses only if the self-test also failed |
| `require` | same | as `auto`, except that a source older than 8.0.34 **refuses** (see below) | **Refuses**: the deployment relies on compression (a WAN link); message quotes `SET PERSIST binlog_transaction_compression = ON` and the `my.cnf` key | **Refuses** |
| `skip` | nothing | — | — | — |

**Source version floor 8.0.34.** When the source reports a version from 8.0.20 to 8.0.33 (`BinlogTransactionCompressionPreflight.writesOversizedPayloads(String)`: major 8, minor 0, patch < 34; an unparseable or missing version is never classified) the server can write a compressed payload above the 1 GiB replication packet limit that no reader can receive (§3.1 item 4, `BinlogTransactionCompressionPreflight.OVERSIZED_PAYLOAD_HAZARD`). With the source ON that is a WARN banner in `auto` and a refusal in `require`, naming the upgrade and `SET PERSIST binlog_transaction_compression = OFF`; with the source OFF in `auto` it is a WARN not to enable compression on that server. 8.0.34+, 8.1+, 8.4 and 9.x are not flagged.

An unrecognised mode refuses startup naming the three values. The probe is read-only and issues exactly one statement (through `KeylessTablePreflight.assertReadOnlySql`), never a `SET`: the connector cannot and does not turn compression on — that is the source operator's change — it reports whether the source has it and proves it can consume it. The self-test proves the whole chain a compressed transaction needs: that the TRANSACTION_PAYLOAD decoder class the runtime actually loaded is the connector's streaming decoder (`BinlogTransactionCompressionPreflight.streamingDecoderMarker()` reads `STREAMING_DECODER` reflectively from the class loaded under Debezium's name — Debezium's stock class has no such field, so a classpath on which it shadows the connector's is detected and reported with the class's code-source location), the zstd-jni classes, a loadable native library for this platform, and the decoder itself, by decoding a synthetic payload (one XID event inside a zstd frame) through `TransactionPayloadDeserializer` constructed as Debezium constructs it (`BinlogTransactionCompressionPreflight.decodePayload(byte[])`) and iterating — never indexing — its inner events. A stock decoder on the classpath fails the self-test: it would decode small transactions but stop the connector permanently on the first one above 2 GiB, so it is treated like a missing decoder in the table above.

Three gauges are set after the probe (never in `skip`): `clickhouse_sink_source_binlog_transaction_compression` (1 ON, 0 OFF, -1 unknown), `clickhouse_sink_source_binlog_transaction_compression_level_zstd` (-1 unknown), `clickhouse_sink_binlog_payload_decoder_ok` (1 passed, 0 failed). They are set on every engine start, so a source change picked up at the next restart is visible; between restarts the value is what the source reported when this engine started.

Per-event observability (how many payloads were decoded, compressed vs uncompressed bytes) is not available to the connector: the change event does not say whether its row came from a payload, and the embedded engine exposes no hook on the binlog client. The source side has it (`Transaction_payload_event` rows in `SHOW BINLOG EVENTS`, the compressed/uncompressed sizes in `mysqlbinlog --verbose`); the end-to-end harness (§5) uses the former as its proof that compression was exercised.

### 3.5 Versioning: the rest of the same event is not a redelivery
The version sequence (spec 02.02 §3.1) classifies a positioned record against the run's high-water mark: above it — first delivery, floored; the same event — the rest of that event, floored at what its first row received (§3.1.2); below it — redelivery, not floored. "The same event" is decided by `SourcePosition.sameLogPosition` — same log, same file, same byte position, **any row index** (spec 01.02 §3.3) — and that test is made BEFORE the above/below comparison.

The row index cannot take part in that decision. Under a payload the second statement's rows arrive at `(F, P, 0)` when the mark is `(F, P, a)` from the first statement's last row; by `compareTo` they rank below the mark. If they were treated as redeliveries they would keep their raw statement time while the first statement's rows had been floored, and a transaction that inserted, updated and deleted one key would version its INSERT above its own UPDATE and DELETE: the update lost, the deleted row live, row counts intact. Two things make that concrete rather than theoretical: the floor is above the raw statement time exactly when it matters — after every restart, when it is seeded from the durable mark (about one to six source seconds above the last version) or from the connector clock plus five seconds on the first start after an upgrade (spec 02.02 §3.5) — and one large multi-row statement is by itself several rows events with restarting row indexes, so a plain bulk `INSERT … VALUES` followed by an `UPDATE` in the same transaction is enough. Both paths are affected, because the GTID path versions with the same clamped timestamp (spec 02.01 §3.1).

With the same-event rule every row of a compressed transaction is floored at what its first row received and versioned by the strictly increasing counter, in delivery order — which is binlog order, which is commit order. The mark is left at the first row that set it; a redelivery of the whole transaction (engine retry without a restart) meets the same mark and takes the same clamp, so the assignment stays redelivery-stable (spec 02.04 §3.3). A redelivery from an EARLIER event keeps the un-floored, source-timestamp anchored assignment, whatever its row index. Uncompressed multi-row events, which always had rows above the mark at the same position, receive exactly the versions they received before (the first-delivery clamp to `sequenceMaxSourceTs` and the same-event clamp to `sequenceHighWaterEffectiveTs` coincide within one transaction, because no other record is versioned between two rows of one transaction).

### 3.6 What does not change
Schema evolution, DDL handling, the DDL barrier, TRUNCATE, keyless tables, offsets and the durable version mark are untouched: a DDL is its own (uncompressed, statement-format) transaction and reaches the dispatch loop as before; inner rows events are dispatched to the same handlers as uncompressed ones. The connector's own writes to ClickHouse are identical in shape and content for a compressed and an uncompressed delivery of the same transaction — compression is a property of the transport from the source, invisible in the replica.

## 4. Invariants Preserved
- **Invariant I1 (Log Sequence Monotonicity)** and **I2 (Deterministic Version Monotonicity)**: within a compressed transaction delivery order is binlog order, and the same-event rule keeps the versions of its rows strictly increasing above the floor; across transactions the first row of the next payload is a first delivery above the mark.
- **Invariant I8 (Durable Offset Quiescence)**: an offset inside a payload never advances past an unwritten row (§3.3); a restart re-delivers, never skips.
- **Invariant I9 (Loud Failure)**: a source that compresses while the decoder is unavailable refuses at start, with the fix in the message, instead of failing on the first payload with a deserialization error; `require` refuses a source that does not compress.
- **Invariant I11 (Drop-in Upgrade Safety)**: the version formula, seeds and domain are unchanged (spec 02.01 §4); only the classification of same-event rows changed, and only for rows that were mis-classified.
- **Read-only against the source**: the preflight issues one `SELECT` and never a `SET`; compression is enabled by the source operator, never by the connector.
- **No transaction-size limit on a source at 8.0.34+ (§3.1 item 4)**: a compressed payload is at most 1 GiB and is streamed; a transaction whose compressed payload would exceed 1 GiB is written uncompressed by the source and arrives as ordinary events. A source older than 8.0.34 is flagged at start (§3.4).
- **Bounded memory per transaction (§3.2.1)**: the heap a compressed transaction costs the decoder is its compressed size (≤ the source's 1 GiB replication packet limit) plus the decompressor's window plus one inner event, independent of its uncompressed size; there is no uncompressed-size limit on the connector's side. Downstream of the decoder the change events flow through Debezium's byte-bounded queue and the handoff cap (spec 01.05) exactly as for an uncompressed transaction.
- **Compressed equals uncompressed**: a compressed transaction dispatches the same events, in the same order, with the same data, as the stock decoder produced for it; only when and how often they are held in memory differs.

## 6. Failure Modes & Recovery
Compression changes the transport, not the pipeline: every failure below recovers through the same durable-offset restart as an uncompressed stream, with ONE compression-specific cost -- a restart inside a payload redelivers the whole transaction (§3.3), so the re-apply part of the recovery time is proportional to the in-flight payload's UNCOMPRESSED size (measured: 2.4 GB in 37 s, 4.6 GB in 54 s, §3.1 item 4). Measured recovery times come from the chaos harness (§5), run on the 2.11.0 head plus spec 01.09, MySQL 8.0.46, ClickHouse 24.8, connector heap 4 GiB, eight writers plus a ~1.5 GB payload writer; the value is the time from the fault's removal until a marker committed on the source after it is in ClickHouse -- restart, redelivery and the catch-up of everything written during the fault. Objective (Invariant I15): 300 s plus the re-apply of the in-flight transaction.

```
phase  fault (under load)                          GTID on   GTID off   before spec 01.09
I0     source idle 200 s (> read timeout)          3 s, 0 restarts   3 s, 0 restarts   -
F1     kill -9 of the connector mid-payload        18 s      18 s       17 s
F2     RST on the binlog connection                18 s      19 s       18 s
F3     partition until the source gives up         14 s      14 s       never (300 s window)
F4     ClickHouse stopped 60 s                     191 s     188 s      191 s
F5     ClickHouse frozen 150 s                     21 s      21 s       21 s
F6     MySQL clean restart                         5 s       5 s        5 s
F7     mysqld kill -9 while a payload commits      10 s      5 s        never (421 s window)
F8     GLOBAL compression toggled 12x under load   0 s       1 s        -
F9     five kill -9 of the connector, 20 s apart   1 s       3 s        16 s
F10    3 MB/s link while a payload streams         3 s       2 s        3 s
F11    20 ADD/DROP COLUMN rounds under inserts     1 s       2 s        1 s
```

- **FM-01.08-1 Connector killed or restarted inside a payload**.
  - **Detection**: the process exit (supervisor) or "Engine stopped with an error"; on restart "Skip 0 events / Skip k rows on streaming start".
  - **Blast radius**: none lost; the whole in-flight transaction is redelivered and deduplicated by version (§3.3, §3.5).
  - **Recovery**: automatic (in-process restart, or the supervisor's process restart).
  - **RTO**: measured 17-18 s with a ~1.5 GB payload in flight (F1), 1-16 s after the fifth of five kills 20 s apart (F9); plus the re-apply of the payload (~12 s per GB uncompressed).
  - **Test**: chaos F1, F9; large L3; hard H9.
- **FM-01.08-2 Binlog connection closed by the source, or dead behind a partition, while payloads stream**.
  - **Detection**: the binlog connection guard's ERROR and metric (spec 01.09).
  - **Blast radius**: none lost.
  - **Recovery**: automatic (spec 01.09).
  - **RTO**: measured 5-10 s after mysqld came back from kill -9 (F7), 14 s after a partition healed (F3), 18-19 s after an RST (F2). Before spec 01.09, F3 and F7 never recovered by themselves.
  - **Test**: chaos F2, F3, F7; `BinlogConnectionGuardTest.aPeerCloseOnARealSocketThrows()`, `BinlogConnectionGuardTest.aSilentPeerFailsTheClientWithinTheTimeout()`.
- **FM-01.08-3 ClickHouse down or frozen while payloads are applied**.
  - **Detection**: WARN "Retriable ClickHouse error ... retried in N ms" per batch (backoff to 30 s), then ERROR "Could not persist the version high-water horizon ... (attempt 30/30)" and an engine stop.
  - **Blast radius**: replication pauses; nothing lost.
  - **Recovery**: automatic once ClickHouse answers.
  - **RTO**: 21 s after a 150 s freeze (F5); 188-191 s after a 60 s stop (F4). F4 is dominated by the engine stop the connector starts when the high-water horizon cannot be persisted: Debezium waits out its coordinator shutdown (90 s) and its executor shutdown (90 s) while the event thread is held, then the engine restarts. Within the objective; GAP: the engine stop could release the event thread at once and cut F4 to about the ClickHouse outage plus 20 s.
  - **Test**: chaos F4, F5.
- **FM-01.08-4 Compression switched on and off at run time; mixed and varying-level streams**.
  - **Detection**: nothing to detect -- decoding is per event type (§3.1 item 3).
  - **Blast radius**: none.
  - **Recovery**: none needed.
  - **RTO**: 0-1 s (F8, 12 GLOBAL toggles under load; session-level OFF and levels 1-22 throughout the writer mix).
  - **Test**: chaos F8 and the writer mix; hard H6.
- **FM-01.08-5 A single row too large for the connector's heap** (a LONGBLOB/LONGTEXT/JSON value of hundreds of MiB inside a payload -- the decoder holds one inner event, §3.2.1, and Debezium materialises the row's images; since spec 03.06 §3.4 the writer no longer renders them as text in memory, it streams them to a spill file).
  - **Detection**: the JVM exits on `OutOfMemoryError` ("Terminating due to java.lang.OutOfMemoryError: Java heap space" with `-XX:+ExitOnOutOfMemoryError`, exit code 3); without that flag, a GC-bound JVM that makes no progress.
  - **Blast radius**: replication stops at the transaction; nothing is acknowledged past it; the supervisor's restart re-reads it.
  - **Recovery**: since spec 03.06 §3.4, measured with `sink-connector-lightweight/tests/e2e/large_row_spill.sh` (one row inserted and updated in one transaction, i.e. three images of the value in one payload, 4 GiB heap): with `binary.handling.mode=bytes` rows of 64, 128, 256 and 512 MiB are value-exact with no `OutOfMemoryError` (heap after GC at most 2.6 GiB at 512 MiB), where 2.11.0 before §3.4 exited on the 256 MiB row in 2 of 3 runs and crash-looped on the restart; with `binary.handling.mode=base64` (the Ansible template's setting) 64 and 256 MiB are value-exact at 4 GiB and 512 MiB needs more than 4 GiB (value-exact at 8 GiB, heap after GC 3.1 GiB). Before it (measured E5, 256 MiB row, 4 GiB heap: four of six runs exited on OOM, and again 2 of 3 on 32b43c2b, whose restarts crash-looped) the heap had to be well over 16x the largest row. A row whose decoded images do not fit still loops on the restart until the heap is raised (`-Xmx`; from the measurements above, 8x the row was enough with `bytes`, and with `base64` 8x was not and 16x was).
  - **RTO**: one restart when marginal; operator-bound otherwise (a heap change and a restart).
  - **DEFECT** (residual): the row's decoded images (the inner event body, Debezium's per-image copies, and with `base64` their Base64 strings) must fit the heap; no connector setting bounds them and the failure is an `OutOfMemoryError` loop, not a named refusal. The writer's share -- measured with JFR as 17.5 of 22.4 GiB allocated for a 64 MiB and a 256 MiB row -- is gone (spec 03.06 §3.4).
  - **Test**: edge E5 (passes at 4 GiB since §3.4); `large_row_spill.sh`.
- **FM-01.08-6 Binlog purged past the connector's offset while it was down**.
  - **Detection**: ERROR "Engine stopped with an error: cause: Cannot replicate because the source purged required binary logs..." within 5 s of the start (edge E8, GTID on), then the retry budget and a terminal exit; nothing is skipped silently.
  - **Blast radius**: replication stops; the purged transactions are gone from the source's binlog.
  - **Recovery**: reposition to the source's current position and re-synchronise every captured table from MySQL (`ch-mysql-resync`, spec 11.04). A reposition of an EXISTING replica must run with `enable.snapshot.ddl=false` (the production template's value): with `true` (this repository's docker default) the schema-only start executes Debezium's `DROP TABLE IF EXISTS` + `CREATE TABLE` for every captured table and EMPTIES the replica (measured E8: 300,339 live rows to 0).
  - **RTO**: the re-synchronisation of the captured tables (spec 11.04). Measured E8 for one small table: 176 s wall time from the stop to convergence, of which up to 130 s is the harness's own fixed settle wait; the reposition kept the replica's 300,339 existing rows with `enable.snapshot.ddl=false`.
  - **Test**: edge E8.
- **FM-01.08-7 A payload the decoder refuses** (corrupt, truncated, size mismatch, ZSTD without an uncompressed size, nested payload; a pre-8.0.34 source's oversized payload the server cannot send).
  - **Detection**: `PayloadEventDecodingException` in "Engine stopped with an error", terminal after the retry budget; for the oversized pre-8.0.34 payload, the source's `ERROR 1236`/"Event too big" and the preflight's WARN/refusal at start (§3.4).
  - **Blast radius**: replication stops at the payload; nothing after it is acknowledged; nothing is partially applied (§3.2.1 item 5).
  - **Recovery**: fix the cause; if the transaction cannot be read at all, move past it (`sink-connector-client change_replication_source` to the next transaction -- see spec 09.03 for the state of that command) and re-synchronise the tables it touched (spec 11.04).
  - **RTO**: operator-bound (a stop that needs a decision); the re-synchronisation of the touched tables.
  - **Test**: `StreamingTransactionPayloadTest.sizeMismatchFailsLoudly()`, `StreamingTransactionPayloadTest.truncatedFrameFailsLoudly()`, `StreamingTransactionPayloadTest.zstdPayloadWithoutUncompressedSizeIsRefused()`, `BinlogTransactionCompressionPreflightTest.sourceOnBefore8034WarnsInAutoAndRefusesInRequire()`.
- **FM-01.08-8 Cross-version downgrade mid-payload (new in the 3.1.3.Final to 3.7.0.Final upgrade, PR #1558; §3.3; corrected 2026-10, PR #1558 regression sweep)**. A connector built from Debezium 3.3.2.Final or later (this branch, post-upgrade) that crashes while applying a compressed transaction commits a durable offset with `event = n > 0` (the count of inner events of that payload already completed). If the connector is then downgraded to a build on Debezium older than 3.3.2 (2.11.0 and earlier, pre-upgrade) and resumes from that same offset, the old build's `handleTransactionPayload` dispatches inner events directly rather than through `handleEvent`, so the `skipEvent` flag it sets at the inner `BEGIN` (because `initialEventsToSkip = n != 0`) is never cleared **via a decrement** for the rest of that payload: every remaining rows event of the WHOLE payload is skipped, not just the `n` already-completed ones. The inner `XID` still resets `skipEvent = false` (normal commit bookkeeping), but it does so *before* the outer `TRANSACTION_PAYLOAD` event's own post-dispatch `if (skipEvent) { --initialEventsToSkip; }` check runs, so that check finds `skipEvent` already `false` and **decrements nothing at all** -- `initialEventsToSkip` survives this entire payload completely unchanged at `n`, not `n - 1`. If the next top-level binlog event is itself another compressed transaction, the whole sequence repeats: that payload is skipped in its entirety too, and `n` again survives unchanged. **This repeats for every subsequent fully-compressed transaction, without limit, until enough uncompressed top-level events (which ARE individually routed through `handleEvent` and so do decrement the budget by 1 each while `skipEvent` is armed) have been processed to exhaust `n`** -- and because each transaction's own commit clears `skipEvent` early if `n` is not yet exhausted, that consumption can itself be spread across several subsequent uncompressed transactions, each needing its own `BEGIN` to re-arm the flag. Net effect: rows that were never applied are permanently lost from replication, with no error and no log distinguishing this from a normal skip-on-restart. The reverse direction (a <3.3-written offset, always `event = 0`, resumed by a >=3.3 build) is safe -- see §3.2 item 3 -- this is a one-way hazard specific to downgrading.
  - **Detection**: none at the time it happens -- the log lines ("Skip N events on streaming start") look identical to a normal, correct restart. Only a downstream row-count/checksum divergence against the source (spec 02.04-style audit) would surface it, and only if one is run.
  - **Blast radius**: the unapplied tail of the one in-flight compressed transaction (which can be the bulk of a large transaction, as in hard case H9's 1.2M-row example), PLUS every subsequent fully-compressed transaction in its entirety for as long as `skipEvent` keeps getting re-armed without a matching decrement (unbounded -- not a fixed handful of outer events), PLUS a final partial run of uncompressed top-level events (rows, DDL, or other transactions' events, possibly spanning more than one subsequent transaction) sufficient to exhaust the original `n`-sized budget -- chosen by whatever happens to follow in the binlog, not by anything related to the lost transaction.
  - **Recovery**: do not downgrade across a crash boundary inside a compressed transaction. If a downgrade after such a crash is unavoidable, first reset the stored offset's `row`/`event` to 0 against the same `file`/`position` using the fork's own offset-edit tooling (`DebeziumOffsetStorage.updateBinLogInformation`, `sink-connector-lightweight/src/main/java/com/altinity/clickhouse/debezium/embedded/cdc/DebeziumOffsetStorage.java` lines ~238-299, already zeroes both whenever a file+position pair is supplied) -- this degrades the resume to the old build's own whole-payload redelivery behavior (safe, at-least-once, §3.3 historical paragraph) instead of the skip-everything failure; then re-synchronise (spec 11.04) only if a later audit finds divergence, since the degraded resume itself does not lose rows. **Verified loss-free live** (2026-10, PR #1558 regression sweep, `s6_bug1_workaround` below): value-exact (value-level compare EQUAL) after applying this reset and resuming with the old build. Forward (same-version-or-newer) restarts are never affected.
  - **RTO**: not time-bound -- this is a silent data-loss defect, not a stop; recovery is whatever a later row-count/checksum audit's remediation costs (spec 11.04 resync of the affected tables), if and when the loss is even noticed.
  - **Test**: **reproduced live (2026-10, PR #1558 regression sweep)** with an out-of-tree end-to-end harness (isolated container, Percona 8.4, `binlog_transaction_compression=ON`) in addition to the source-analysis reading above. `s6_bug1_noworkaround` (JAR_A=branch-final 3.7.0.Final, JAR_B=2.11.0/3.1.3.Final): JAR_A was `kill -9`'d mid an 800-row compressed transaction (6/800 rows applied, resumed offset `{"row":1,"event":12,...}`); JAR_B then streamed the remaining attempt tail plus two more fully-compressed transactions (60 rows each) and one final uncompressed transaction (20 rows). Result: `mysql=1140` vs `clickhouse=220` -- 920 rows permanently lost, spanning the original payload's tail AND both of the two subsequent, otherwise-unrelated compressed transactions, with only the final uncompressed transaction's rows getting (partially) applied once the `n`-budget was exhausted. This confirms **reading (a)** -- unbounded loss across every subsequent fully-compressed transaction -- and refutes the bounded "`n-1` subsequent outer events" reading this entry previously carried: a bounded reading cannot explain two entire, independent, later compressed transactions losing 100% of their rows. `s6_bug1_workaround` (same JAR_A/JAR_B pair, but `row`/`event` reset to 0 against the same `file`/`position` before starting JAR_B, per the Recovery bullet below): `mysql=1140` vs `clickhouse=1140`, value-level compare EQUAL -- the documented workaround is confirmed loss-free. `s6_upgrade_direction` (JAR_A=2.11.0/3.1.3.Final, JAR_B=branch-final 3.7.0.Final, i.e. the reverse/forward direction): `mysql=1140` vs `clickhouse=1140`, EQUAL -- confirms the forward direction (§3.2 item 3) is safe, consistent with 3.7's `handleTransactionPayload` routing every inner event through its own full `handleEvent` call (including its own `completeEvent()`/skip-decrement), which old-build-written offsets never raced ahead of.
  - **DEFECT** (cross-version only; forward and same-version restarts are unaffected and are the only paths this repository's own builds exercise in production use).

Summary: 8 failure modes, 2 DEFECT, 1 GAP.
