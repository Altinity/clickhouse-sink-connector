| ddl.primary.key.rebuild                                   | **Optional**, Default: true. When a source `ALTER TABLE` changes a table's row identity (`ADD PRIMARY KEY` of a different column set, `DROP PRIMARY KEY`, or `DROP PRIMARY KEY, ADD COLUMN id ... AUTO_INCREMENT, ADD PRIMARY KEY (id)`), the connector rebuilds the ClickHouse table under the new sorting key as MySQL rebuilds its clustered index for the same statement (Spec 06.09). The **swap** runs inside the DDL barrier and is metadata-only: an empty table with the new key is created and exchanged into place, the old table is retired under the name `<table>__pk_rebuild_<ts>` (or `<table>__pk_retired_<ts>` in a non-Atomic database), and replication of every table resumes at once. The **copy** of the pre-DDL live rows (versions preserved) then runs online on the `pk-rebuild-backfill` thread, partition by partition, followed by a completeness check; only then is the retired table dropped and the log reports the backfill complete. Until that line, a value-level comparison of the table is expected to differ and the retired table still exists; a failed backfill step is logged at ERROR (and recorded in the error table when `error.logging.enable=true`) and retried with backoff (10 s doubling to 5 min) without stopping replication, and a restart resumes it from the retired table. A replicated statement-level truncate or drop of the table (or of its database) that arrives while its backfill is still pending cancels the backfill and drops the retired copy and key map before the statement runs, so the rows the source removed are never copied back (Spec 06.09 §3.3.2 step 7) -- also under `disable.drop.truncate=true`. Values only the source knows (an `AUTO_INCREMENT` key column added by the statement) are read from MySQL with a read-only `SELECT`. `disable.drop.truncate=true` keeps the retired copy instead of dropping it. With `false` the statement is refused loudly, nothing is emitted for it and the manual rebuild is named (Spec 06.07). |
| exit.on.terminal.failure                                  | **Optional**, Default: true. Once the embedded engine has failed `errors.max.retries` times in a row, replication is stopped for good; with `true` the process exits with code 3 so a supervisor restarts or alerts on it, with `false` it stays up with replication stopped (`/status` reports `Replica_Running=false`, a FATAL line is logged). It never idles silently. The retry budget refills when the engine makes progress (an offset acknowledged to Debezium since the previous failure), never merely because a restart came up: an engine that starts cleanly and dies again on the same record every time is failing in a row. |
